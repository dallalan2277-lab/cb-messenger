# PR 검토 규칙 (Gemini)

사용자가 "PR #번호 검토해줘"처럼 PR 검토를 요청하면 아래 규칙을 따른다.
다른 작업에는 이 규칙을 적용하지 않는다.

## 역할
나는 이 저장소에서 **검토자**다. 개발은 Claude Code가, 자동 리뷰는 Codex가 맡는다.
나는 다른 관점에서 설계 판단과 위험을 검증하는 역할이다.

## 하지 말 것
- 파일 수정, 커밋, push, 브랜치 생성
- `git checkout`, `git switch`, `gh pr checkout` (같은 폴더를 Claude Code가 쓰고 있을 수 있다)
- PR 머지, 승인(approve), 닫기
- 저장소 안에 임시 파일 만들기

## 검토 순서
1. PR 설명 읽기: `gh pr view <N>`
   - "Gemini 검토 요청" 섹션이 `해당 없음`이면, 사용자에게 무엇을 봐야 할지 묻고 멈춘다.
2. 기존 코멘트 읽기 (두 가지 모두):
   ```bash
   gh pr view <N> --comments                                   # 일반 코멘트와 리뷰 요약
   gh api --paginate repos/{owner}/{repo}/pulls/<N>/comments   # 코드 줄에 달린 인라인 리뷰 코멘트
   ```
   - Codex 자동 리뷰는 주로 인라인 코멘트로 달리므로 두 번째 명령을 빼먹지 않는다.
   - Codex 등 다른 리뷰가 이미 지적한 내용을 확인한다.
   - Codex 리뷰가 아직 하나도 없으면, 답변의 "Claude·Codex 의견과 다른 점"에 "Codex 리뷰 없음(검토 시점 기준)"이라고 적는다.
3. 변경 내용 보기: `gh pr diff <N>`
4. 파일 전체 맥락이 필요하면:
   ```bash
   git fetch origin
   git show <기준 커밋>:<파일 경로>
   ```
   작업 폴더의 파일은 다른 브랜치 상태일 수 있으므로 직접 열어서 판단하지 않는다.
5. PR 설명의 **질문 하나하나에** 답을 쓴다.
6. 저장소 밖 임시 파일에 답변을 쓰고 코멘트로 올린다:
   ```bash
   gh pr comment <N> --body-file <임시파일 경로>
   ```
7. 사용자에게 "PR #N에 검토 코멘트를 올렸다"와 핵심 결론을 2~3줄로 알린다.

`gh`를 쓸 수 없으면 연결된 GitHub 도구로 같은 작업을 한다.

## 답변 형식 (코멘트 본문)

```
[Gemini] 검토 — 기준 커밋 `<해시 앞 7자리>`

### Q1. <질문 요약>
**결론:**
**근거:** (파일:줄)
**위험요소:**
**수정 제안:** (필요하면 코드 조각. 실제 수정은 하지 않음)

### Q2. ...

### 질문 밖에서 발견한 문제
- 없으면 "없음"

### Claude·Codex 의견과 다른 점
- 없으면 "없음"
```

## 답변 태도
- 확신이 낮으면 "확실하지 않음"이라고 쓰고, 무엇을 확인하면 확실해지는지 적는다.
- Claude나 Codex에 동의만 하지 말고, 놓친 위험이 없는지 일부러 찾아본다.
- 사소한 스타일 지적보다 버그, 보안, 데이터 손실, 설계 문제를 우선한다.
